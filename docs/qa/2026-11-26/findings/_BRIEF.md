프로젝트 규칙: JiuJitsuConnect/CLAUDE.md. 계획: docs/qa/2026-11-26/PLAN.md (사용자 8명 페르소나 P1~P8, 심각도 P0~P3 정의가 있다 — 먼저 읽어라).

## 환경
- 실제 서버·로그인·웹 화면은 못 띄운다(시크릿이 가짜). 그래서 **코드를 사용자 시나리오대로 따라가며** 깨지는 경로를 찾는다.
- 웹(FE)이 그리는 화면은 범위 밖. iOS 네이티브 코드와 웹↔앱 브리지(WebBridge)만 본다.
- **소스 파일을 고치지 마라.** 쓰는 파일은 네 결과 파일 하나뿐이다. 빌드도 돌리지 마라(다른 점검자와 DerivedData 충돌).

## 하는 법 — 적대적으로
- "버그가 있다"고 가정하고 찾는다. 페르소나별로 실제 손가락 동작을 상상해 상태 전이를 하나씩 따라간다.
  연타·취소·뒤로가기·시트 내리기·백그라운드 전환·네트워크 실패·빈 값·서버가 예상 밖 값을 줄 때·권한 거부·큰 글씨·VoiceOver.
- Reducer의 모든 Action 경로, 에러 처리(catch에서 상태 복구되는지, isLoading이 풀리는지), 중복 요청 방지, 취소(CancelID), 상태 초기화를 본다.
- 사용성: 막다른 길, 되돌릴 수 없는 행동에 확인이 없음, 헷갈리는 문구, 피드백 없음(저장됐는지 모름), 접근성 라벨 누락.
- **추측 금지.** 각 결함은 file:line 근거와 구체적 재현 순서가 있어야 한다. 확신이 낮으면 confidence를 낮게 적어라.
- 의도된 설계(주석·커밋 메시지에 이유가 적힌 것)는 결함이 아니다. `git log -S`/`git log --follow`로 의도를 확인할 수 있다.
- 양보다 질. 진짜 결함 몇 개가 오탐 스무 개보다 낫다. 그래도 범위의 모든 화면·흐름은 한 번씩 다 밟아라.

## 결과 파일 형식 (한국어, 마크다운)
맨 위에 `# <묶음 ID> <묶음 이름> 점검 결과`, 그 아래 `## 점검한 흐름` (밟은 흐름 목록과 각 흐름 OK/문제 한 줄씩 — 통과한 것도 적는다),
그 다음 `## 결함` 아래 결함마다:

```
### <묶음ID>-<번호> [P0|P1|P2|P3] 한 줄 제목
- 페르소나: P2 급한 손
- 재현: 1) … 2) … 3) …
- 기대 / 실제: …
- 근거: JiuJitsuConnect/Targets/…/X.swift:123 (필요하면 코드 몇 줄 인용)
- 고치는 방향: (한두 줄) · 분류: [코드수정-화면변화없음 | UI논의필요 | 웹/서버 확인필요 | 사람이 실기기 확인]
- 확신도: 높음|중간|낮음
```

마지막에 `## 실기기에서 사람이 확인할 것` (코드로는 판단 못 하는 항목 체크리스트).
최종 답변은 결과 파일 경로와 결함 개수(심각도별)만 짧게.
