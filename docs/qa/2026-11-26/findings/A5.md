## 결함

### A5-1 [P1] 홈 상세 모달 위에서는 로그인 안내 알럿이 안 보이고, 로그인 창도 뜨지 않음
- 페르소나: P8 떠나는 사람(게스트로 둘러보기), P1
- 재현:
  1) 게스트로 홈 피드에서 웹이 `OPEN_SUBVIEW(presentation=modal)`로 여는 글을 연다(전체 화면 상세 모달).
  2) 그 안에서 좋아요 · 댓글 등 로그인이 필요한 행동을 누른다(웹 → `AUTH_LOGIN_PROMPT`).
  3) 아무 반응이 없다. 모달을 닫으면 그제서야 "로그인하고 좋아요를 눌러 보세요" 알럿이 탭 화면에 떠 있다.
  - 변형 A: 웹이 `AUTH_LOGIN_MODAL`(다이렉트)을 보내면 `loginCover`가 세워지지만 모달이 이미 떠 있어 로그인 창이 보이지 않는다.
  - 변형 B: 로그인한 사람이 상세 모달을 보다 세션이 만료 → 모달 위 만료 알럿(이건 모달 위에 그림) → [로그인] → 로그인 창이 안 뜸. 게스트 전환은 상세 모달을 닫지 않는다.
  - 변형 C: 상세 모달 안 대회 상세의 '내 기록에 남기기'(게스트) → 같은 로그인 창 경로.
- 기대 / 실제: 기대 — 지금 보고 있는 모달 위에 로그인 안내/창이 뜬다. 실제 — 알럿은 아래 탭 화면 오버레이에 그려져 모달에 가려지고, 로그인 창은 같은 뷰의 두 번째 `fullScreenCover`라 이미 떠 있는 상세 모달 때문에 표시되지 않는다(SwiftUI는 한 뷰에서 한 번에 하나만 띄움).
- 근거:
  - `Presentation/Sources/Features/AppTab/AppTabView.swift:151-160` — `loginCover`와 `home.detailCover`가 같은 뷰에 나란히 붙은 `fullScreenCover`.
  - `Presentation/Sources/Features/AppTab/AppTabView.swift:197-203` — 로그인 안내 알럿은 탭 화면에만 그림. 같은 이유로 기기 알림 · 만료 · 탈퇴 알럿은 `isInCover` 쌍을 두었다(`:176-186`, 주석 "아래 탭 화면의 알럿이 모달에 가려지므로 모달 위에 그린다").
  - `Presentation/Sources/Features/Community/CommunityFeature.swift:656-660,791-794` — 모달 상세의 로그인 요청도 그대로 AppTab으로 올림.
  - `Presentation/Sources/Features/AppTab/AppTabFeature.swift:489-491` — `showLoginModal`은 상세 모달을 닫지 않고 `loginCover`만 세움. `AppTabFeature+Session.swift:101-114` `resetToGuest`도 `detailCover`를 닫지 않음.
- 고치는 방향: 로그인 안내 알럿에도 `isInCover` 쌍을 두고(만료 알럿과 같은 방식), 로그인 창은 상세 모달 안에서 띄우거나(모달 쪽에 `fullScreenCover` 하나 더) 띄우기 전에 상세 모달을 닫는다. · 분류: 코드수정-화면변화없음 (+ 사람이 실기기 확인: 웹이 실제로 modal로 여는 화면에서)
- 확신도: 중간 (코드 경로는 확실, 게스트에게 modal 상세가 실제로 열리는지는 웹 사용처에 달림)

### A5-2 [P2] 소셜 창 단계에서 두 로그인이 겹치면 늦게 끝난 쪽이 진행 중인 서버 로그인 위에 덮이고, 저장 토큰과 화면 계정이 갈릴 수 있음
- 페르소나: P2 급한 손
- 재현:
  1) 로그인 첫 화면에서 '카카오로 계속하기'를 누르고, 카카오톡으로 넘어가기 전(또는 Google 창이 올라오기 전) 바로 'Google로 계속하기'도 누른다. SNS 단계는 버튼이 막히지 않는다.
  2) 두 SNS가 모두 성공하면 `socialLoginResponse(.success)`가 두 번 와서 서버 로그인이 두 번 나간다. 이 액션에는 `isLoading` 확인이 없다.
  3) 둘 다 기존 회원이면 먼저 끝난 계정으로 `didLogin` → 탭 화면이 그 계정으로 만들어짐. 늦게 끝난 서버 로그인도 `AuthRepositoryImpl.serverLogin`이 토큰을 키체인에 저장 → 화면(authInfo · 웹 주입 토큰)은 A 계정, 네이티브 API · 다음 자동 로그인은 B 계정.
  - 변형: 서버 로그인 진행 중에 뒤늦게 온 SNS 실패(`socialLoginResponse(.failure)`)가 `handleError`에서 `loadingProvider = nil`로 로딩을 풀어 버튼이 다시 눌린다.
- 기대 / 실제: 기대 — 로그인 하나가 서버 단계에 들어가면 다른 SNS 결과는 버린다. 실제 — 마지막 결과가 그대로 진행되고 토큰 저장도 그대로 된다.
- 근거: `Presentation/Sources/Features/Login/LoginFeature.swift:139-145` (성공 처리에 가드 없음), `:147-148,255-256` (실패가 로딩을 무조건 해제), `Data/Sources/Repositories/AuthRepositoryImpl.swift:171-178` (서버 응답이 오면 바로 저장)
- 고치는 방향: `socialLoginResponse`에서 `state.isLoading`이면 성공 · 실패 모두 무시(실패는 로딩 해제도 하지 않음). · 분류: 코드수정-화면변화없음
- 확신도: 중간 (코드 경로는 확실. 두 SNS 창이 실제로 둘 다 성공까지 가는지는 실기기에서 확인)

### A5-3 [P2] '모두 동의하기'가 선택 항목(마케팅)까지 켜서, 마케팅을 빼려던 사람이 모르고 동의하게 됨
- 페르소나: P2 급한 손, P5
- 재현:
  1) 약관 시트에서 '서비스 이용약관' · '개인정보 처리방침'만 직접 체크(마케팅은 일부러 안 함), '만 14세'는 깜빡함.
  2) 아래 버튼이 '모두 동의하기'로 남아 있어 누른다 → 마케팅까지 체크되고 버튼이 '다음'으로 바뀜.
  3) 같은 자리에 손가락이 있어 바로 '다음' → `isMarketingAgreed = true`로 가입.
  - 변형: '모두 동의하기' → 마케팅만 해제 → 필수 하나를 실수로 해제했다 다시 '모두 동의하기' → 해제해 둔 마케팅이 다시 켜짐.
- 기대 / 실제: 기대 — 필수만 빠졌을 땐 필수만 채우거나, 사용자가 직접 끈 선택 항목은 건드리지 않는다. 실제 — 버튼 하나가 '필수 미완료'와 '전체 동의'를 겸해 모든 행을 켠다.
- 근거: `Presentation/Sources/Features/TermsAgreement/TermsAgreementFeature.swift:46-48,97-103` (`state.rows.ids.forEach { ...isChecked = true }`, 선택 항목 포함). 전체 동의 후 화면에 머무는 것은 주석상 의도(`:99`)지만 필수 일부만 빠진 경우는 다루지 않음.
- 고치는 방향: 같은 버튼 자리에 '다음'과 '모두 동의하기'가 번갈아 오는 구조와 마케팅 포함 여부를 디자인 · 기획과 정한다(예: 필수만 남았을 때는 필수만 켜기). 광고성 정보 수신 동의는 명시적이어야 하므로 법무 관점도 확인. · 분류: UI논의필요
- 확신도: 높음 (동작) / 결함 여부는 정책 판단

### A5-4 [P2] 약관 항목을 VoiceOver로 체크할 수 없거나 체크 상태를 알 수 없음, 상세 버튼에 이름 없음
- 페르소나: P6 접근성
- 재현: 1) VoiceOver 켜고 신규 가입 → 약관 시트. 2) 항목을 쓸어 넘기면 체크 아이콘 · 제목 · '필수'가 따로 읽히고 버튼 · 선택됨 여부가 나오지 않음. 3) 오른쪽 `>` 버튼은 이름 없이 이미지 이름 또는 "버튼"으로 읽힘.
- 기대 / 실제: 기대 — "서비스 이용약관 동의, 필수, 선택됨/선택 안 됨, 버튼"과 "서비스 이용약관 전문 보기, 버튼". 실제 — 행 전체가 `onTapGesture`가 붙은 HStack이라 버튼 특성 · 선택 상태 · 묶은 라벨이 없고, 상세 버튼에 `accessibilityLabel`이 없음.
- 근거: `DesignSystem/Sources/Component/BottomSheet/TermsAgreementSheetRowView.swift:38-59` (onTapGesture, 접근성 수식어 없음), `:65-74` (chevron 이미지 버튼 라벨 없음)
- 고치는 방향: 왼쪽 묶음을 `Button`으로 바꾸거나 `.accessibilityElement(children: .combine)` + `.accessibilityAddTraits(.isButton)` + `isChecked`면 `.isSelected`, 상세 버튼에 "\(title) 전문 보기" 라벨. · 분류: 코드수정-화면변화없음
- 확신도: 중간 (실기기 VoiceOver로 읽는 내용 확인 필요)

### A5-5 [P3] 서버가 닉네임을 형식 오류(R0004)로 거절하면 이유와 상관없이 "한글/영문/숫자, 2~12자로 작성해 주세요"

- 재현: 1) 앱 규칙은 통과하지만 서버가 막는 닉네임(예: 금칙어 · 운영자 사칭 단어 · 'admin' 등 — 서버 정책에 따라)을 입력 → 확인. 2) 서버가 R0004로 거절. 3) 화면은 "한글/영문/숫자, 2~12자로 작성해 주세요" — 이미 지킨 규칙을 다시 지키라고 안내.

### A5-6 [P3] 중복 확인 · 가입이 네트워크 오류로 실패하면 입력한 닉네임이 자리표시자 회색으로 바뀜

### A5-7 [P2] 가입 요청이 시간 초과로 끝났는데 서버엔 계정이 생겼으면, 다시 '확인'할 때 내 닉네임이 "이미 사용 중"으로 나오는 막다른 길
- 페르소나: P3 지하철
- 재현: 1) 닉네임 '사용할 수 있는 닉네임이에요' 확인 뒤 다시 '확인'(가입 요청). 2) 응답이 30초를 넘겨 시간 초과(서버는 처리 완료). 3) 토스트 뒤 다시 '확인' → 상태가 `.networkError`라 가입이 아니라 중복 확인부터 → 방금 내 계정이 쓴 닉네임이라 "이미 사용 중인 닉네임이에요". 4) 다른 닉네임으로 바꿔 가입하면 이미 쓴 임시 토큰으로 요청 → 서버 응답에 따라 일반 오류 반복. 사용자는 뒤로가기 → 그만두기 → 같은 소셜로 다시 로그인해야 들어갈 수 있다는 걸 알 수 없음.
- 기대 / 실제: 기대 — 시간 초과 · 연결 끊김 뒤엔 "가입됐는지 확인 중" 또는 같은 소셜로 다시 로그인하도록 안내. 실제 — 중복 닉네임 안내로 끝남.
- 근거: `Presentation/Sources/Features/NicknameSetting/NicknameSettingFeature.swift:278-286,353-360` (실패 시 `.networkError` → 다음 탭은 `checkNickname`, `:198-223`), 타임아웃 `Data/Sources/Network/Endpoint.swift:46-48`
- 고치는 방향: 서버가 같은 임시 토큰의 재가입 요청에 어떻게 응답하는지(멱등/A0003/기타) 확인 후, 시간 초과면 그 닉네임으로 바로 가입을 다시 보내거나 재로그인 안내. · 분류: 웹/서버 확인필요
